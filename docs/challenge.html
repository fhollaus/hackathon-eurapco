Claims

Handles medical reimbursements. A claim here is a reimbursement record, not an accident.

The policyholder writesThe agentInsurer decides?
“What is the status of claim CL-H001?”Reads the existing record and explains it. Already works in the baseline.No
“Please reimburse this specialist visit.”Checks the policy is active, the patient is insured, the date is inside the coverage period, the evidence is complete and the invoice was not already reimbursed. Then calculates and pays.Yes, if the reimbursement is above EUR 1,500

Covered: specialist consultation, diagnostic test, physiotherapy. Not covered: dental care, cosmetic treatment, medicines. Evidence is text inside the JSON, never a PDF.

Two human interactions

Sometimes the system must stop and ask a person

There are exactly two kinds of question. Each can happen at most once per request, and they are separate: a request may need both, one, or neither. Do not ask when you do not need to.

1 · Asking the policyholder

Clarification

When

The request is clear but something required is missing: “change my address” without a postal code, or a diagnostic test without its prescription text.

Your system

Asks one question that collects all the missing items, then stops and waits.

Who answers

You, playing the policyholder: send a clarification reply with the missing information. You may not change any fact already in the request.

Then
  • No reply yet: the request keeps waiting. Waiting is not a failure.
  • Reply still not enough: close the request without the blocked action. Never ask twice.
  • If you cannot tell what the person wants (unclear), explain and close with no question. There is no “are you sure?” step.

2 · Asking the insurer

Authorization

When

The request is allowed but too large to do alone: limit above EUR 5,000, deductible above EUR 200, reimbursement above EUR 1,500 (exactly at the threshold needs no authorization), or any termination.

Your system

Builds a precise proposal (what exactly, with which values), saves it, then stops and waits.

Who answers

You again, as the insurer's representative, with an insurer_decision event: approve or reject, and a reason when rejecting.

Then
  • Approved: execute exactly the saved proposal, nothing else.
  • Rejected: do nothing and explain the reason.
  • No revision, no different amount, no second round. An approval cannot make an unsupported or excluded request allowed.
While you develop, you choose the replies, including invalid or insufficient ones, to test your system, always without changing supplied facts. In the common test the instructions tell you how to answer, and the insurer's decisions are fixed. Event formats: docs/contracts.md and examples/events/.

Your job

What you receive

  • Two executable agents with monolithic prompts and working enquiry flows: agents/administration/ and agents/claims/.
  • A deliberately basic keyword router (app/router.py), functioning MCP client (app/mcp_client.py) and server (mcp_server/).
  • Nine domain tools with technical validation and narrow simulated effects: docs/tools.md, code in app/domain.py.
  • Fictional policies and history, with a fresh copy for every new request: data/initial.json, rules in docs/policy.md.
  • Text evidence inside JSON, message and tool schemas, fixed common vocabularies: contracts/.
  • An implemented cumulative JSON evaluation logger: app/evaluation.py.
  • Skill-loading support and empty domain skill folders: app/skills.py and skills/.
  • 15 public tickets, from straightforward to more complex: examples/training/.

What your team builds

  • Improve the router and classification, and organize your harness around the common scope. Starting point: app/router.py.
  • Use the minimum-information matrix (docs/minimum-information.md) to collect genuinely missing information once.
  • Implement workflow state, correlation and stop/resume for human replies. Keep the same domain run and original facts; never restart a reply as a new request. Starting point: app/runtime.py, which handles the first message only; event formats in docs/contracts.md and examples/events/.
  • Enforce admissibility, active-policy and date checks, authority and proposal integrity. Rules: docs/policy.md.
  • Implement deterministic Claims calculation and duplicate prevention. Formula and duplicate key: docs/policy.md.
  • Write and use at least one meaningful skill per agent. The loader exists (app/skills.py); the procedures are yours, in skills/.
  • Design the reimbursement-record lifecycle: when to register a record, how to update outcomes, when a workflow ends without a new record. The tools create_claim, pay_claim and record_claim_outcome are in docs/tools.md.
  • Connect your workflow, classification and human events to the supplied logger (app/evaluation.py).
  • Communicate actual results, not intended effects, and keep the enquiries working.
Framework, workflow storage, interaction channel and UI are your choices. Additional tools and traces are optional. No monitoring, cost mapping or deployment is required, and no particular UI, framework or extra trace earns points by itself.

Three things, kept apart

Every request is described by a request category, an agent state and a request outcome

Request category

What was asked?

Identifies the requested operation.

Where you find it

request_categories in vocabulary.json · request_category in the log

What it is for

We compare it with the expected category for each message of the common test.

What your team does

Classify every message correctly: improve the router (app/router.py) and set the category before the request waits, completes or closes.

Agent state

Where is the agent in handling the request?

Identifies the state of the agent process that is handling the request.

Where you find it

agent_states in vocabulary.json · agent_state in the log

What it is for

It shows whether the request is being processed, is waiting for a person or is finished. A request that asks a person must pass through a waiting state.

What your team does

Your system must check and set the agent state at every step, including stop and resume for human replies. The baseline only handles the first message.

Request outcome

What happened to the request?

Identifies the result.

Where you find it

request_outcomes in vocabulary.json · request_outcome, reason and message in the log

What it is for

We check it against the real tool results and the final data snapshot in the log.

What your team does

Report the actual result of each request, never the intended one, and explain it in reason and message.

Already in the repo: the three lists, the checks that reject unknown values (contracts/*.schema.json) and the logger that stores them (app/evaluation.py). Your system decides which value each request gets.

2 · Agent states

The same six agent states for both agents

The state of the agent process that is handling the request. List: agent_states in vocabulary.json.

Agent stateMeaning
processingCurrently handling the request
awaiting_clarificationSuspended, waiting for the one policyholder reply
awaiting_authorizationSuspended, waiting for the insurer decision
completedFinished with an answer, a successful effect or a coherent team-defined completion
closed_without_executionClosed without the requested effect; the request outcome explains why
failedA technical failure prevented normal completion
Your system must check and set the agent state. You may keep richer internal states, as long as you map them to these six in the log.

Your evidence

Every message produces one JSON log

We evaluate the results in these logs and the pitch you give. The log records what actually happened, not what the model says happened.

One log per initial request

A clarification reply or an insurer decision is another event in the same request: it is added to the same log, not a new one. When the request waits, the log shows the waiting state; after the reply, the same log is updated until the final result.

Supplied

The logger already exists. You connect your workflow to it; you do not write the JSON yourself.
